# Bringup 验证代码评估与处理建议

## 评估范围

本文针对当前 `feature/hardware-bringup` 分支上的 bringup 验证代码做工程评估。
本轮评估基于仓库中的脚本、现有文档和官方 SDK 例子对照，不包含本轮重新上真机复测。

评估对象主要包括：

- `scripts/bringup/check_arx5_import.py`
- `scripts/bringup/check_arx5_state.py`
- `scripts/bringup/check_arx5_min_motion.py`
- `scripts/bringup/arx5_joint_slider_gui.py`
- `scripts/bringup/arx5_keyboard_cartesian_teleop.py`
- `scripts/bringup/_arx5_common.py`

## 当前代码的定位

这套代码适合被定义为 bringup / 运维验证工具，而不是后续新功能的长期工程主线。

它已经解决了当前阶段真正需要解决的问题：

- 验证 `arx5-interface` 在目标机器上的导入、配置和通信链路。
- 在默认不运动的前提下读取关节状态和末端状态。
- 用非常小的、可控的动作验证关节控制链路。
- 提供简单人工遥控入口，方便 bringup 阶段做联调和排障。

从阶段目标看，这套代码是有效的。
从长期软件结构看，它还不适合继续生长成主系统。

## 做得对的部分

### 1. 复用了官方 SDK 的控制主路径

当前脚本没有重写底层控制协议，而是复用了官方 Python SDK 的核心对象和调用方式。
这比自己再造一层未验证的控制抽象稳妥得多。

### 2. 安全约束是明确的

当前脚本普遍有以下约束：

- 默认 `plan_only`
- 需要 `--execute`
- 需要确认短语或显式确认
- 从实测状态启动，而不是直接跳到硬编码姿态

这很符合 bringup 阶段的风险控制方式。

### 3. 对实验室实际操作友好

脚本支持 JSON 输出、无头环境检查、GUI 和键盘遥控两种入口。
这说明代码不是只面向一次性验证，而是已经考虑了现场使用。

## 当前工程上的主要限制

### 1. 它是脚本集合，不是稳定包边界

现在的重心还在 `scripts/bringup/`。
`_arx5_common.py` 已经承担了共享运行时职责，但它仍然只是脚本辅助模块，不是正式包接口。
这会带来两个问题：

- 后续代码一旦继续复用这里的函数，很容易把临时脚本层变成事实上的核心库。
- 外部模块无法明确知道哪些接口是稳定承诺，哪些只是 bringup 期间的内部辅助。

### 2. CLI 协议在多个脚本里重复展开

`--execute`、`--yes`、`--json`、`plan_only`、安全提示等约束在多个脚本里重复存在。
现在规模还小，还能靠人工保持一致。
后面一旦再加新入口，行为漂移的概率会明显上升。

### 3. 输入层和控制会话层耦合在一起

`arx5_joint_slider_gui.py` 和 `arx5_keyboard_cartesian_teleop.py` 里，界面输入、状态同步、目标更新、下发节奏和控制器调用都在同一层。
这对 bringup 很直接，对长期维护不友好。
后面如果要再加 Web UI、ROS2 节点、远程 RPC 或自动化测试，这种结构复用价值很低。

### 4. 部分行为依赖当前 SDK 的实现细节

例如 `check_arx5_min_motion.py` 里对 `reset_to_home()` 时长的估计，实际上依赖当前 SDK 的语义和当前机械臂状态。
这类逻辑适合作为临时验证脚本里的经验处理，不适合作为长期系统行为假设。

### 5. 原生输出捕获方案比较脆弱

`NativeOutputCapture` 通过进程级 stdout/stderr 重定向去压住 SDK 的原生日志输出。
这个办法对当前 JSON 输出问题是有效的，但它属于工程妥协，不是很稳的长期基础设施。
后面如果引入更多线程、更多原生扩展，维护成本会增加。

## 为什么不建议把它作为新 feature 的继续演进基线

后续如果项目要做正式功能，通常需要这些边界：

- 稳定的 SDK 适配层
- 可测试的控制会话层
- 明确的任务 / 动作编排层
- 可替换的操作入口层，例如 CLI、GUI、ROS2、服务接口

当前 bringup 代码还没有按这些边界切开。
如果直接在它上面继续堆功能，最容易出现的结果是：

- bringup 脚本继续膨胀
- 共享辅助函数越来越像隐式框架
- 每加一个入口就复制一遍参数、安全门和控制循环
- 最后很难判断哪些代码是实验室脚本，哪些代码是正式产品路径

这不是代码能不能跑的问题。
这是后续维护成本和系统边界会不会失控的问题。

## 建议的处理方式

### 1. 把这套代码保留为“已验证的 bringup 资产”

建议保留的角色是：

- 硬件接线和通信验证脚本
- 实验室联调脚本
- 运维排障脚本
- 回归烟雾测试脚本

建议不要再把新 feature 直接加进 `scripts/bringup/`。

### 2. 新功能从新的包结构开始

后续新 feature 建议从独立区域开始，例如：

```text
src/armctrl/
  adapters/arx5/
  control/
  teleop/
  applications/
```

一个更清晰的职责划分是：

- `adapters/arx5/`：只负责 SDK 适配、状态读写、控制器封装
- `control/`：只负责控制会话、目标管理、安全策略、轨迹或插值逻辑
- `teleop/`：只负责 CLI / GUI / 输入设备适配
- `applications/`：只负责具体应用入口

这样 bringup 阶段验证过的逻辑可以逐步迁移进去。
迁移的是稳定经验，不是整套脚本结构。

### 3. 对 bringup 代码采用冻结策略

推荐做法是：

- 只修 bringup 脚本里的硬件兼容性和明显缺陷
- 不再往里面追加新业务能力
- 文档中明确标注它是验证和运维工具，不是长期主线架构

## 是否并入 `develop`

结论：不要把当前 `feature/hardware-bringup` 整体当成后续功能开发基线并入 `develop`。

更合适的处理方式有两种。

### 方案 A：需要长期保留硬件验证能力

如果你希望以后在 `develop` 上仍然保留一套可直接执行的硬件 smoke test / bringup 工具，那么可以并入 `develop`，但前提是把它当成隔离的验证资产。

这意味着：

- 只把它视为 `docs/bringup/` 和 `scripts/bringup/` 下的验证工具
- 不让新 feature 继续依赖这套脚本结构扩展
- 文档明确标注“validation only”或同等含义

这种并入是为了保留验证能力，不是为了继承架构。

### 方案 B：后续不会再沿用这套入口

如果后续新 feature 会在新的包结构里重做，而当前脚本只承担阶段性 bringup 验证，那么不建议整枝并入 `develop`。

更合适的处理是：

- 保留 `feature/hardware-bringup` 分支
- 打一个清晰标签，例如 bringup 里程碑标签
- 把评估和操作文档保留下来
- 未来只按需摘取个别经验或脚本

这种方式更干净，也更符合“阶段性验证代码”和“长期产品代码”分层管理。

## 推荐结论

按当前项目意图，推荐采用下面的策略：

1. 不把当前 bringup 分支作为新 feature 的起点。
2. 是否并入 `develop`，只看你是否要把它作为长期保留的验证工具集。
3. 如果只是阶段性验证成果，保留分支和文档，不必整枝并入 `develop`。
4. 如果确实需要未来持续使用这套验证脚本，再把它以隔离目录的方式并入 `develop`。

当前这套代码值得保留。
但它更适合作为“验证资产”，不适合作为“长期主线”。
